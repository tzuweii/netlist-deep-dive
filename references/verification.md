# 驗證方法論

分析結果可信與否，取決於**驗證方法本身可不可信**。工具鏈自己的假設若錯了，
所有 PASS 都沒有意義。

---

## 三層驗證

### 第 0 層：parser 沒有漏讀

最底層。`Netlist.selfcheck()` 用完全獨立的邏輯重數一次原始檔：

| 檢查 | 通過的意義 |
|---|---|
| `*PART*` 行數 vs parts 數 | 沒有元件被吞掉 |
| `*SIGNAL*` 數 vs nets 數 | 沒有網路被吞掉 |
| `refdes.pin` token 數 vs `nets` 收錄數 | 沒有腳位被吞掉 |
| **`refdes.pin` token 數 vs `pinmap` 收錄數** | **沒有腳位被覆蓋** |
| 同名 `*SIGNAL*` 數 | 0 表示沒有網路互相覆蓋 |
| 幽靈 refdes | 出現在 `*NET*` 但 `*PART*` 沒有 → 0 表示兩區塊自洽 |
| 未歸類行 | 0 表示沒有格式沒被處理到 |

⚠️ **第四項是後來補的，缺它會漏掉一整類錯誤。** 同一支腳出現在兩條 net 時
（設計短路或匯出錯誤），`pinmap` 只能留一個值、第一條 net 靜默消失；但
token 數與 `nets` 收錄數**兩者都仍然相等**，所以舊版回報 PASS。
只有比對 `pinmap` 的收錄數才抓得到。

任何一項不過，**先修 parser，不要往下做**。

### 第 1 層：元件模型對得上 datasheet

追跡結果完全建立在模型上。這一層有**三種強度不同**的檢查，不可混淆：

| 檢查 | 能證明什麼 | **不能**證明什麼 |
|---|---|---|
| `verified_against` 必填 | 有人聲稱翻過那一頁 | 那一頁真的寫了這件事 |
| pin-existence（模型的腳存在於 netlist） | 沒打錯腳號、沒套錯腳數不同的衍生型號 | **封裝對不對** |
| package 解析 | 用的是哪一欄腳位表 | 那一欄的功能解讀正確 |

⚠️ **pin-existence check 不是封裝驗證。** 兩個封裝同為 1–N 而腳位定義不同時
（這是常態），它必然通過。命名要誠實——名字若叫「封裝驗證」，名字本身就在
製造假保證。

`load_models()` 會拒絕載入沒有 `verified_against` 或 `package_basis` 的模型。
**這個限制是刻意的，不要為了讓追跡跑通而繞過它**——追跡停在某顆 IC，是
「這裡還沒查證」的正確表現。

#### package 解析：三階惰性

只在**會改變答案**時解析：

| 階 | 情況 | 成本 |
|---|---|---|
| 1 | datasheet 腳位表只有一欄 → `not_applicable` | 零。且這是**已證明**無歧義，不是假設 |
| 2 | 觀測腳位集 ⊆ 某欄合法集且唯一 → `auto_unique` | 零 |
| 2b | 所有候選在用到的腳上**功能一致** → `shared_pinout` | 零 |
| 3 | 多欄皆可容納／抽取失敗 → `unresolved_pending_user` | 問一次，只問這顆 |

**不得以已接腳數推定封裝**（見 `pitfalls.md` #13）。抽取失敗時進第 3 階，
不得退回腳數猜測。

### 第 2 層：內容斷言

把文件裡每一條可機械驗證的主張寫成 `assertions`。可用的 kind：

| kind | 驗什麼 |
|---|---|
| `count_pn` | 某料號共幾顆 |
| `pin_net` | 某顆某腳接到哪條網路 |
| `pin_net_seq` | 連續腳位對連續網路（`{i}` / `{i-1}` 代入） |
| `bom_value` | BOM 的值含某字串（電阻值等） |
| `not_stuffed` | 這幾顆是 DNI |
| `net_pin_count` | 某網路掛幾支腳 |
| `net_count` | 符合 pattern 的網路有幾條 |
| `single_pin_nets` | 懸空網路總數（可加 `all_from` 限定來源料號） |
| `i2c_addr` | 由位址腳反推的 I2C 位址 |
| `net_exists` | 某網路存在 |

加上 `role_rules` 把 `U<n>03` 這種通則展開逐顆比對。

**首次執行的 FAIL 就是文件的錯。** 改文件，不要改斷言遷就；改完後把斷言改成
驗證「更正後的事實」，並在文件裡誠實記錄「首次 N 條中 M 條 FAIL」——
之後重跑全 PASS 是「已修正」的結果，不是「首次就全對」。

## 跨板對接：枚舉排名

netlist 沒有跨板連線，對接是**推論**。驗證方式不是「兩側相符」，而是
**枚舉所有合理對應並排名**。

兩個指標分工：

- **矛盾腳數** — 一側 GND、另一側是訊號這種直接打架。0 才可能成立。
- **語意相符數** — net 名稱正規化後相同的腳數。用來在「都沒有矛盾」的候選之間分勝負。

哪個指標有效，取決於兩側的命名狀況：

| 情況 | 有效的指標 |
|---|---|
| 一側 net 是自動命名（`N#####`） | 只能靠矛盾腳數 |
| 兩側都有意義命名 | 靠語意相符數 |
| GND 分布對稱（多列連接器） | 矛盾腳數失效，**必須**靠語意 |

**margin ≤ 4 就要在文件裡標明證據薄弱。**

### 先分辨對接的物理型式

`ndd.py mate` 會依兩側連接器型號自動判斷並標註：

| 型式 | 意義 | 定案途徑 |
|---|---|---|
| 兩側同型（例如都是公頭 terminal） | 公頭無法互接 → **中間必然有線束** | 線束圖或 continuity |
| 公母直接對接 | **沒有線束** | 只剩 footprint 方位 → 查 layout |

兩者完全不同，不要混為一談。

### 用「會不會壞」排除殘存候選

排名後若還有多個候選，把每個代入看它會造成什麼故障：

- 若某候選會讓 I2C 的 SDA/SCL 對調 → I2C 全滅
- 若某候選會讓 SPI 的 DIN/DOUT 對調 → 寫不進去

系統若實際能跑，這些候選就被排除了。**這是唯一同時涵蓋 layout 正確性的證據**
——因為它驗的是實體行為，不是檔案內容。

## 結構上驗不到的四類

工具再怎麼加也驗不到這些。`REVIEW.md` 會固定列出來。

| 類別 | 例子 | 為什麼驗不到 | 怎麼補 |
|---|---|---|---|
| **因果推論** | 「這個 RC 造成約 4 ms 延遲」「這個拓樸是為了匹配路徑長度」 | netlist 不含設計意圖 | 實測，或問設計者 |
| **實體板狀態** | rework、飛線、換料 | `.asc` 是設計，不是那一片板 | 查該片的 rework 紀錄 |
| **layout 決定的量** | 阻抗、插入損耗、耦合、串音、footprint 方位 | 不在 netlist 裡 | layout 檔或實測 |
| **專案外資料** | 自製 IC 的封裝腳位表、線束圖 | 檔案根本不在手上 | 向外取得 |

⚠️ **第二、三類最容易被忽略**：即使改版「電路設計完全沒變」，只要 layout 或
材料變了，量測數值就不能跨版本沿用；而 netlist 推導的結論則可以。
交付時要把這條界線講清楚。

## 交付時要說的話

不要用「全部通過」交付。要分開講：

> **A 段（工具驗得到，已通過）**：parser 自我驗證、N 條內容斷言、命名規則展開、
> DNI 對帳、懸空網路。
>
> **B 段（工具驗不到，需要你人工確認）**：腳位模型是否真的翻過 datasheet、
> 證據薄弱的對接、rework 紀錄、線束、BOM 變體、文件裡的因果推論。

`ndd.py review` 會把這兩段寫成 `REVIEW.md`；`ndd.py coverage` 給 per-MPN 的
三源覆蓋表。

### 兩個獨立的軸，不要混講

| 欄位 | 值 | 回答的問題 |
|---|---|---|
| `confidence` | `confirmed > caveated > unknown` | 這條結論的**證據**有多強 |
| `gating` | `always` / `conditional` / `unknown` | 這條路徑**已查證**的通斷性質 |

一條 datasheet 查證完整、package 已鎖定的 runtime-gated 路徑，證據品質是
`confirmed`、通斷性質是 `conditional`。把兩者混成一個排序，會讓它排在
「package 未佐證但恆通」之下——與事實相反，而且會誘使人為了拉高 confidence
而迴避正確標註的 conditional。

### 正式 trace 與 topology hint 不可互換

`signal_chain.csv` 只含**已驗證的 signal_transfer 邊**，可作架構結論。
`topology_hint.csv` 是控制、狀態、參數與未知邊界的**功能說明**——
它不是連通關係，**永不得作為下一跳**。
