# 已知結構性失敗模式

這份文件**不是判讀規則，也不是操作 checklist**。它描述 `netlist-deep-dive` 這套
分析架構在實際使用時，特別容易產生「看起來合理、但其實錯誤」結果的通例。

怎麼產生答案在 `SKILL.md`；**這裡只管答案會怎麼壞掉**。

## 三段，三種用法

| 段 | 何時作用 | 怎麼用 |
|---|---|---|
| **輸出觸發器**（6） | 寫答案的當下 | 對著**正在寫的句子**比對，不是記在心裡 |
| **格式事實**（5） | 讀到那種編碼時 | 對著**看到的資料**比對 |
| **背景認識**（7） | 開始分析前讀一次 | 帶著走，**答完不重掃** |

不要求逐條回報。**「誰擋著」欄寫「無」的才需要我親自守**——已被程式擋住的，
忘記也不會出事。

# 輸出觸發器

寫下符合左欄形狀的句子時，右欄的檢查就要跑。**這不是自我監控，是模式比對。**

## T1 句子裡出現「腳位名 + 動詞」

致能、輸出、驅動、量測、選通⋯⋯

**檢查**：這句的來源必須是 `[D 檔名 p.x]`，不能是 `[S]`。
**為什麼**：名稱由人取、由工具改，命名慣例可能與實際功能脫節。`.DSN` 證明這支腳
**叫什麼**，datasheet 才證明它**做什麼**。
**為什麼看起來合理**：名稱帶很強的工程直覺，`X` → `X` 的功能幾乎不像在推論，
像在讀。慣例愈普遍愈危險——`EN` 幾乎總是對，所以不會被當成推測。
**誰擋著**：無。

## T2 句子裡把腳數／顆數當成理由

**檢查**：這個數字是完整集合，還是目前觀測到的集合？**數量只能排除候選，
不能證明候選。**
**為什麼**：`pinmap` 完全由 `*NET*` 建立，NC 腳結構上不會進去。
`len(pins(refdes))` 一律是**已接腳數**——netlist 裡不存在「元件總腳數」。
**為什麼看起來合理**：它的產物是一張**完整、漂亮、全錯**的腳位對應。24 腳件
只接 20 支就被判成 20 腳封裝，之後每一支腳都對錯位置。
**誰擋著**：`resolve_package()` 用包含關係而非基數——但那只保護工具路徑，
不保護我手算。

## T3 描述的鏈路經過 control／stateful 腳

**檢查**：這是 `signal_transfer` 還是 `control_influence`？後者**不是**下一跳。
**為什麼**：netlist 天然是 connectivity graph，「A 能改變 B 的行為」與「訊號 A
經 B 到 C」在圖上長得一樣。
**為什麼看起來合理**：control 腳真的連到那顆 IC，output 也真的存在。串成 path
在圖論上很自然，在電路上完全不存在——`LOAD -> Q outputs` 是物理上不存在的鏈路。
**誰擋著**：`signal_chain.csv` 與 `topology_hint.csv` 分檔，BFS 只走 transfer 邊。
**但我用散文描述鏈路時不經過那道閘。**

## T4 寫下否定句：「沒有」「找不到」「不存在」「消失」

兩個檢查，都要跑：

**(a) 涵蓋範圍**：這個來源保證「若 X 存在就一定出現在這裡」嗎？沒有保證，
absence 就不是否定證據。BOM 只涵蓋它定義的零件類別；model／endpoint／mate
可能只是還沒宣告。
**(b) 設定**：是電路真的沒有，還是 configuration 把它排掉了？
`power_net_regex`、`bom_scope`、`mates`／`mate_map`、`endpoints`、`part_class`、
`net_normalize` ——**這些設錯的共同症狀不是多出錯誤，是結果變少**，而且輸出
反而更乾淨。
**誰擋著**：判定 2 涵蓋 BOM；電源軌有落點爆量當反向警報。**其餘四個旋鈕全無。**

⚠️ 兩個檢查都過之後，「沒有」就是**可交付的結論**，不需要加但書——見 T5。

## T5 答案裡出現 `[D 缺]`／`unknown_stop`／「無法判定」

**檢查**：這是查過之後的結論，還是沒查就宣告？並且——**停在哪一顆的哪支腳，
講出來了嗎？**
**為什麼**：其餘所有條目都指向懷疑。全部同時生效時，預設行為會漂成「不下結論」，
而那在輸出上看起來像嚴謹。
**為什麼看起來合理**：拒絕回答永遠不會被抓到錯——它的成本落在使用者身上，
不落在答案的正確性上。
**誰擋著**：無。

實測過的三種過度保守：

- 位址腳看起來像普通電源腳 → 以為無從查證，其實翻腳位表就有，還能由 netlist
  反推驗算。
- 把「沒有模型」一律當 `unknown_stop` → 89 種主動料號裡 74 種是真終端，
  `loads` 欄會接近全空。
- 因為 BOM 標成某個變體就拒絕下結論 → **那是把工具的保守當成嚴謹**。

> **「不可得」必須有根據，不能是沒查就宣告。** 停在具名位置是有用的答案，
> 猜出來的完整鏈路是有害的答案——但**沒查就說不可得，兩種都不是**。

## T6 兩個**獨立**來源對同一件事說了不同的話

**檢查**：衝突本身要**講出來**，不能默默選一個——尤其不能挑「看起來比較對」的
那筆。
**什麼算獨立**：判準是「這兩份資料是不是從同一個東西產生的」。
BOM（採購端）vs netlist（原理圖端）、datasheet（原廠）vs symbol（設計者手建）、
使用者宣告 vs netlist、同料號兩顆的 symbol 腳位名——**這些來源獨立，能衝突**。
**什麼不算**：`.DSN` vs `.asc` 是同一份設計的兩種匯出，**不一致一律是轉換 bug，
不是衝突**。實際抓到的三個都是轉換器的錯（`GetIsGlobal` 少傳參數、
`IsNetlistIgnore` 語意誤解、拿「沒有 pin」當排除規則會誤刪 47 顆真零件）。
**為什麼**：真正的衝突表示有一邊過期或建錯——那是**給設計者的資訊**，
不是我該私下裁決的事。
**誰擋著**：偵測由工具做（封裝矛盾 `audit [1.5]` FAIL、`Bom.of()` 重複 refdes
回 sentinel、`pinfn` 對名不符攤開兩邊且不寫快取、`init` 對帳硬失敗）。
**我負責的是工具攤開之後不要順手挑一個**——默默採用 datasheet 那筆，等於把
錯誤封裝的腳位名凍結成資產。

# 格式事實

以下不是推理失敗模式，是 `.asc` / `.DSN` 的**編碼方式**造成的誤導。
**推不出來、程式擋不住、讀到資料當下就會撞上**——只能靠讀過。

- **PADS 會把 net 整條改名。** `.asc` 不收 `*`、`/` 這類字元，formatter 遇到就
  把整條 net 改成 `X#####`（實測 `GPU_SYS_RESET*` → `X00697`，七條）。`X00697`
  毫無資訊——設計者取的原名**只存在於 `.DSN`**，要用那個。
- **兩腳網路沒有名字。** 串阻與連接器之間的兩腳網路，OrCAD 給自動編號
  （`N16731502`）。那不是不相符，只是沒名字——先穿過串阻往回解析到有意義的名稱。
- **上劃線是逐字元反斜線。** Capture 用 `P\W\R\D\N\` 表示 `PWRDN` 上有上劃線
  ＝**低有效**。那是設計者明確畫的，可以當 `[S]` 引用。`.asc` 與 `pstchip.dat`
  都不帶這個資訊。
- **腳位名的 `+` / `-` 不可正規化掉。** `SENSE3+` 與 `SENSE3-` 是差動對的兩支
  **不同**腳；一起正規化會讓該報衝突的地方變成靜靜合併，留下哪一個看順序。
- **階層路徑字串不可用分隔符拆。** `hier_path_display`
  （`Power_Seq/LDO Bank #2/U39`）**只給人看**。四片板 14,355 個名稱實測，
  `- \ / 空白 + ( ) #` 全部合法出現過——拆錯不報錯，只會給你一棵看起來合理的
  假階層樹。要層級請用 `Hierarchy.path_of()` 上溯 `parent_id`。

# 背景認識

開始分析前讀一次，帶著走。**答完不必重掃**——這些沒有文字觸發器，
逐條回頭檢查只會變成儀式。

## B1 正確引用不等於正確推論

標記綁定的是「材料哪來的」，不是「從材料到這句話那一步對不對」。四個引用可以
100% 正確，而它們組出的結論仍然是錯的——**而且外觀上比沒有引用的答案更可信**。
`[?]` 不是免責標籤。
**誰擋著**：**無。這是整個設計最大的空洞。**

## B2 證據系統會把目標從「回答問題」帶偏成「容易引用」

`U103 pin 4 接到 NET_A` 極易引用；「為什麼 16 顆相同 IC 形成這個架構」需要綜合，
天然難引用。在引用壓力下答案會漂向前者，最後得到 citation 很漂亮、
工程資訊密度很低的回答。

⚠️ **鬆的是「不要退回只列 refdes」，不是鬆引用。** 架構結論照樣標 `[?]` 並寫出
推理鏈；差別在於推理鏈本身要被檢視，不是有標就算過。
**誰擋著**：無。

## B3 驗證通過，不代表目標問題被辨識

一個檢查可以完全正確，但它驗的東西與真正的問題不同：parser count 對 ≠ 階層對；
pin-existence 對 ≠ 封裝對；byte-identical 回寫對階層錯誤**完全免疫**。

系統的 audit 愈多，愈容易變成「全部 PASS → 結論應該對」。每看到一個 PASS 都要
答得出：**它究竟排除了什麼錯誤？** 排除不了目標錯誤的是 sanity check，
不能升格成 correctness proof。
**誰擋著**：無。

## B4 衍生物看起來正常，不代表仍對應目前來源

CSV、`hier/*.csv`、pin cache、`<板>_Architecture.md` 都是衍生物，可能來自不同
時間的來源。stale data 不是亂碼，是**上一版的正確答案**——比 corrupted data
難察覺得多。過期的階層不會有任何症狀，只會安靜地把零件放錯子電路。
**誰擋著**：只有 `pinfn`（datasheet SHA-256 不符會重抽）。`MANIFEST.md`
**只寫不驗**——`audit` 不比對雜湊，其餘衍生物無任何新舊訊號。

## B5 方向與對稱性不能靠直覺補全

差動對、TX/RX、mux 通道、fanout、連接器列、重複 slot——拓樸高度對稱，於是
「結構相似」很容易滑成「行為對稱」。實際 transfer 可能是 `A → B` 而不是
`A ↔ B`；錯誤的對稱化會在兩個 downstream 之間**製造一條原本不存在的路徑**
（`B3 → 1 → B7`）。
**誰擋著**：`transfer` 邊的 `direction` 必須顯式，沒有預設值；雙向要 datasheet
佐證。未建模的元件不受此保護。

## B6 通則會壓過真正的局部資料

大型系統的重複結構（TX1–TX16、slot 1–N、每組固定 IC）讓 pattern 極容易建立，
然後被套到還沒實際確認的 instance 上。重複結構通常真的存在，而且大部分成立——
危險的是**少數例外長得跟正常 instance 一模一樣**，所以「這顆應該跟其他組一樣」
比亂猜更難察覺。

實測：通則說每 slot 一顆 `A<n>02`，slot 9 因為 `A902`/`A903` 被板級感測器佔走，
跳號到 `A904`。
**誰擋著**：`role_rules` 會展開逐顆比對 BOM 料號——**僅限有設 `role_rules` 的
專案**，其餘無。

## B7 netlist 描述設計，不描述實體世界

`.asc` 精確描述 `refdes.pin ↔ net`，因此容易產生「整塊板都被描述了」的錯覺。
它不含 rework、飛線、換料、footprint 實體方位、阻抗、耦合、串音、裝配錯誤、
現場線束狀態。

當 connectivity 全部對上時，很容易把「設計連線正確」讀成「實體實作正確」。
設計證據、layout 證據、實體板證據、系統行為證據**不能互相取代**——超出範圍就
停在 source capability boundary，不要補一個「最合理」的實體解釋。
**誰擋著**：`REVIEW.md` 固定列出這一項。答題當下無。
