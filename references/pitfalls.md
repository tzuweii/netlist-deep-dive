# 已經踩過的坑

每一條都**實際發生過**，而且每一條產生的都是「看起來完全合理、但是錯的」結論。
排在前面的殺傷力最大。

---

## 1. 憑記憶寫腳位模型 —— 殺傷力最大

追訊號要知道「從這顆 IC 的哪支腳出去」。若模型錯了，追出來的訊號鏈會經過合理的
元件、落在合理的網路上、看起來毫無破綻，但整張表是錯的。

**防法**：`ndd_models.py` 強制每個模型要有 `verified_against`（檔名 + 頁碼 +
文件編號）與 `package_basis`，沒有就拒絕載入。翻 datasheet 的 Pin Configuration
那一頁，不要相信「這顆跟那顆應該一樣」。

**本 skill 不內建任何 seed model** —— 預先建模等於把「你對 datasheet 的解讀」
凍結成看不見的永久資產。

---

## 1b. 對稱的 pair 會捏造不存在的路徑

初版用對稱的 `pairs` 描述導通，於是走圖時兩個方向都能走。後果有兩種，第二種更糟：

- **逆向穿越**：單向緩衝器可以從 output 走回 input。
- **憑空捏造連線**：fanout 的 `1 -> B0..B9` 展開成對稱 pair 後，走圖會走
  `B3 -> 1 -> B7`，於是**兩個輸出之間出現一條實際上不存在的路徑**。

**防法**：改成有向 `transfer` 邊，`direction` 必須顯式（`forward` /
`bidirectional`），沒有預設值。雙向要有 datasheet 佐證。

---

## 2. 「兩側樣式相符」不是對接的證據

驗證連接器 1:1 對接時，若只比對「兩側 GND 腳位置是否相同」，遇到 GND 分布對稱的
連接器（例如 4 列的 SEARAY，GND 在四列完全對稱），**24 種錯誤的列排列會全部通過**。
等於什麼都沒驗到。

**防法**：`ndd.py mate` 枚舉所有合理對應並用兩個指標排名——
「矛盾腳數」（類別打架，0 才可能成立）與「語意相符數」（分勝負）。
只有直通唯一勝出且 margin 夠大才算數。

## 3. netlist 偵測不到 footprint 方位錯誤

netlist 只記錄「refdes.pin ↔ net」，**不含 footprint 的實體方位**。layout 若把
連接器鏡像放置，匯出的 netlist 一個字都不會變，所有名稱照樣完美對上。

> **netlist 證明「接線意圖」，layout 證明「實體位置」，只有系統行為能證明
> 「兩者都對」。三者不能互相取代。**

**防法**：把殘存候選代入，看會不會造成立即而明顯的故障（I2C 對調 → 全滅）。
系統若實際會動，該候選就被排除——這是唯一同時涵蓋 layout 正確性的證據。

## 4. 通則會有例外，而例外正好藏在通則裡

文件為了可讀會寫「每 slot 一顆 `A<n>02` 是 RTD」。實際上 slot 9 的 RTD 因為
`A902`/`A903` 被板級感測器佔走，跳號到了 `A904`——照通則去板上找 `A902`
會找到一顆完全不同的 IC。

**防法**：`role_rules` 把通則展開逐顆比對 BOM 料號。查到的例外登錄進
`known_exceptions`，之後重跑會標成「已知例外」而不是失敗。

## 5. 用檔名猜配對

netlist 與 BOM 的配對、料號與 datasheet 的配對，用檔名 token 重疊去猜會錯，
而且錯了不會有任何跡象（產品線代號、日期都是共通 token）。

**防法**：用**內容**配對。`ndd.py init` 用 refdes 交集率，並在信心不足時明確
標示 `!! 需人工確認`。

## 6. parser 靜靜漏讀

若解析器吞掉幾行，上面所有結論都不成立，而且不會有任何徵兆。

**防法**：`Netlist.selfcheck()` 用完全獨立的邏輯重數一次原始檔，比對
part 行數 / signal 數 / pin token 數 / **pinmap 收錄數** / 重名 / 幽靈 refdes /
未歸類行。已納入 `audit` 的 [0] 段，每次都跑。

⚠️ **pinmap 收錄數這一項專門抓 parser 誤框**：若 `*NET*` 區塊裡有一行沒被認成
`*SIGNAL*` 標頭，它底下的腳會被歸到**前一條 net**；那支腳稍後合法出現時就被
覆蓋掉，而 pin token 數與 nets 收錄數**兩者都仍然相等**，舊版因此回報 PASS。

**這個條件不代表設計短路。** 原理圖工具遇到短路會把兩條 net 合併成一條再匯出，
不會讓一支腳出現兩次。實際成因是 parser 誤框、手改 `.asc`、串接多個檔案、
或非 PADS 2000 方言。發生機率低，但一旦發生，下游全部靜默錯誤。

## 7. 電源網路的正則會吃掉控制訊號

走圖時要排除電源網路（否則整張圖連成一團）。但 `VDD_3V3_P_EN`、`VDD_3V3_P_PG`
這種**名字帶 VDD、實際是控制訊號**的網路會被誤判成電源，導致訊號追不到而
看起來像「這條線沒接到任何地方」。

**防法**：預設的 `power_net_regex` 用負向前瞻排除 `_EN` / `_PG` 結尾。
換專案時檢查有沒有別的命名習慣（`_CTRL`、`_SENSE`…）。

## 8. 名稱正規化把有意義的數字削掉

比對兩側 net 名稱時，若無腦剝掉結尾數字，`CLK_1` 與 `CLK_2` 會變成同一個東西——
於是「A/B 兩列互換」跟「直通」得到相同分數，排名失去鑑別力。

**防法**：`net_normalize` 只剝**階層／slot 後綴**（例如 `_TX_J\d+$`）與共通前綴，
**不要剝功能編號**。改完正規化規則後要重看排名有沒有變得更有鑑別力。

## 9. BOM 類型決定 DNI 判讀

拿到 SMT BOM 時，連接器、測試點、鎖孔本來就不在裡面，它們不是未貼件。
不標註 BOM 類型就會把 68 顆機構件當成 DNI 報出來。

**防法**：`bom_kind` 欄位；`audit` 把 active / passive / 機構分開報，
**只有 `class=active` 且不在 BOM 才是真 DNI**。

## 10. 位址腳被畫成電源腳

I2C 元件的 `A0/A1/A2` 在某些符號裡沒有命名，接到 `VDD`/`GND` 後看起來就是普通
電源腳，讓人誤以為「位址無從查證」。實際上翻 datasheet 腳位表就有，而且可以由
netlist 直接反推位址並驗證。

**防法**：模型的 `addr` 欄位定義 base 與各位址腳權重，`i2c_addr` 斷言自動驗算。
⚠️ 若兩顆同型 mux 只差**一支**位址腳，要在文件裡標明——改板動到那支腳會撞號。

## 11. 兩腳網路沒有名字

串阻與連接器之間的兩腳網路，OrCAD 會給自動編號（`N16731502`）。逐腳比對兩側
net 名稱時，這些會顯示成「不相符」，但其實只是沒名字。

**防法**：比對前先穿過串阻往回解析到有意義的名稱，再比對。不要把自動命名
當成不一致。

## 12. netlist ≠ 你手上那片板

`.asc` 是原理圖匯出，描述的是**設計**。rework、飛線、換料、改版都不在裡面。
另外 layout 決定的量（阻抗、插入損耗、耦合、串音）在改版後不能沿用，
即使電路設計完全沒變。

**防法**：`REVIEW.md` 固定列出這一項。交付結論時明講適用範圍。

## 其他環境層面的坑

- **cp950 終端機**會把中文輸出變亂碼 → 一律加 `PYTHONIOENCODING=utf-8`
- **Git Bash 的 `/c/...` 路徑** Python 讀不到 → 用 `C:/...`
- **CJK 相容表意字**（例如 U+F99C 的「列」，與一般的 U+5217 不同碼）出現在
  資料夾名稱時，Bash 會處理不了 → 用 PowerShell 或 Glob/Read 工具
- **`~$xxx.xlsx`** 是 Excel 開檔時的鎖定檔，掃描時要排除
- **HTTP 200 不代表拿到 PDF** → 見 `datasheets.md`

## 13. 已接腳數不等於封裝腳數

netlist 的 `pinmap` **完全由 `*NET*` 區塊建立**——未接（NC）腳不出現在任何 net，
就永遠不會進 `pinmap`。所以 `len(nl.pins(refdes))` 一律是「已接腳數」，
netlist 裡根本不存在「元件總腳數」這個資訊。

用腳數反推封裝會**系統性低估、穩定偏向較小的封裝**。錯的方向一致，
若測試只用滿接的樣本，永遠看不到。

**已知反例**：24 腳件只接 20 支腳，會被判成 20 腳封裝，然後整張腳位對應全錯。

**防法**：`resolve_package()` 用**包含關係**（觀測腳位集 ⊆ 某封裝欄的合法集）
而非基數。腳數只能「排除」候選，不能「證明」。腳位表抽取失敗時進人工指定，
**絕不退回腳數猜測**。

## 14. 沒有模型不等於訊號在此結束

初版的 `is_terminal()` 是 `return pairs is None`——「沒有模型」直接等於「終端」，
於是一顆未建模型的 bus switch 在 `signal_chain.csv` 裡變成一個**負載**。
這與「回報停在 U6 pin15」正好相反：前者是有害的完整鏈路，後者是有用的答案。

但反過來把「沒有模型」一律當成 unknown_stop 也不行——實測一個系統有 89 種主動
料號、其中 74 種是真正的終端負載，全排除的話 `loads` 欄會接近全空。

**防法**：端點四態（見 `models.md`）。`unclassified` 是**預設值不是結論**，
仍留在 CSV 裡但帶 `endpoint:unclassified` caveat。

## 15. 控制腳被當成訊號路徑

latch / reset / select / OE 會**改變元件行為**，但訊號不會從那支腳穿到輸出腳。
把 `LOAD -> Q outputs` 畫成訊號路徑，得到的是一條物理上不存在的鏈路。

**防法**：`control_influence` 與 `transfer` 是不同欄位，走圖只用後者。
前者輸出到 `topology_hint.csv`，且**不可被 BFS 使用**。正確的敘述是
「此訊號同步觸發 N 個暫存器更新」，不是「此訊號連到那些輸出腳」。

## 16. pin label 集合相同不代表腳位相同

比較兩個封裝欄時，若只比「有哪些 pin 編號」，兩個都是 1–24 的封裝會被判成
「腳位一致、不必問使用者」——但它們的 pin 5 可能是完全不同的訊號。
**這等於把要解決的問題當成答案。**

**防法**：`shared_pinout` 的判定必須比對**腳位功能**（腳位表的名稱欄），
不是只比 label 集合。同理，「模型的 pin 都存在於 netlist」只是
**pin-existence sanity check，不是封裝驗證**——名字若叫錯，名字本身就在製造假保證。

## 17. BOM 範圍決定能不能說「未貼件」

「netlist 有、BOM 無」只有在**完整且會列出 DNP 列的 BOM** 上才等於未貼件。
拿到 SMT BOM 或某個組裝變體時，缺件只代表**不在這份 BOM 的範圍內**。

**防法**：`bom_scope`（`complete` / `smt_only` / `variant` / `unknown`）。
只有 `complete` 能稱為候選 DNI，其餘一律標 `bom-absent:<scope>`。
`not_stuffed` 斷言在 scope 不足時直接 FAIL，回報 `bom-scope-insufficient`——
**不得靜默跳過**，跳過等於用沉默換綠燈。

預設是 `unknown`，**不得為了讓斷言通過而改成 complete**。

## 18. 重複 refdes 靜默覆蓋

BOM 同一個 refdes 出現多列時，後列直接蓋掉前列，而 DNI 對帳與 `not_stuffed`
斷言全都建立在那一次查表上。

**防法**：`Bom.of()` 遇衝突回傳 ambiguity sentinel，相關斷言一律 FAIL 並列出
衝突列號。
