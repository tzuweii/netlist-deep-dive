# 設計說明（給維護工具的人）

這份文件**不在 AI 回答問題時載入**。它收的是兩類內容：

1. **工具已經自動做掉的事**——檢查怎麼做、門檻多少、對照表長什麼樣。AI 回答時
   只需要讀結果，結論已經留在各 reference 裡。
2. **維護者資訊**——為什麼這樣設計、實測資料、刻意不做的事、怎麼新增規則。

改工具之前先讀這裡；改完之後，reference 裡的「結論」如果跟著變了，記得同步。

## 1. 驗證的自動檢查（原 `references/verification.md`）

### 第 0 層：parser 沒有漏讀

最底層。`Netlist.selfcheck()` 用完全獨立的邏輯重數一次原始檔：

| 檢查 | 通過的意義 |
|---|---|
| `*PART*` 行數 vs parts 數 | 沒有元件被吞掉 |
| `*SIGNAL*` 數 vs nets 數 | 沒有網路被吞掉 |
| `refdes.pin` token 數 vs `nets` 收錄數 | 沒有腳位被吞掉 |
| **`refdes.pin` token 數 vs `pinmap` 收錄數** | **沒有腳位被覆蓋** |
| 同名 `*SIGNAL*` 數 | 0 表示沒有網路互相覆蓋 |
| 幽靈 refdes | 出現在 `*NET*` 但 `*PART*` 沒有 → 0 表示兩區塊自洽 |
| 未歸類行 | 0 表示沒有格式沒被處理到 |

⚠️ **第四項是後來補的，缺它會漏掉一整類錯誤。** 同一支腳出現在兩條 net 時
（設計短路或匯出錯誤），`pinmap` 只能留一個值、第一條 net 靜默消失；但
token 數與 `nets` 收錄數**兩者都仍然相等**，所以舊版回報 PASS。
只有比對 `pinmap` 的收錄數才抓得到。

任何一項不過，**先修 parser，不要往下做**。

### 第 0.5 層：階層與 `.asc` 對得上

`.DSN` 轉出來的階層要通過兩道，`init` 才會繼續。**兩道都是硬失敗，不是警告。**

**自我驗證**（`Hierarchy.selfcheck()`）—— 重數一次兩份 CSV 並驗結構不變量：

| 檢查 | 通過的意義 |
|---|---|
| CSV 列數 vs 解析後筆數 | 沒有列被吞掉 |
| `id` 唯一 | 沒有 occurrence 互相覆蓋 |
| 每個 `parent_id` 都指得到 | 階層樹沒有斷鏈 |
| 每個 pin 的 `owner_id` 都指得到 | 沒有孤兒腳位 |
| **自己走 parent 鏈算出的層數 vs API 給的 `depth`** | **兩個獨立來源互證** |
| 必要欄位都在 | 匯出器版本沒有偷偷改欄位 |

⚠️ 最後兩項是重點。`depth` 是 API 直接給的、parent 鏈是我們自己走的——兩者
對不上就代表其中一邊壞了。少了這個交叉，一棵接錯的樹可以完全無症狀地通過。

**與 `.asc` 對帳**（`crosscheck()`）—— 逐條比 net 名、節點集合、零件集合。

`.asc` 是經年累月驗證過的接線權威；階層這條路是新的。兩者描述同一塊板，
**任何不一致都代表其中一邊錯了**。

唯一容許的差異是 PADS 改名：`.asc` 不收 `*`、`/`，formatter 會把整條 net
改名成 `X#####`。**節點集合完全相同**才算改名（工具列出對照表）；節點也不同
就照樣 FAIL。

> ⚠️ **這一層是唯一抓得到「安靜錯誤」的東西。**
>
> 階層寫錯不會讓任何東西崩潰，只會給出**可信但錯誤**的答案。開發期間三個
> bug 全部只被這道對帳抓到，沒有任何一個有其他症狀：`GetIsGlobal` 少傳
> status 參數（`is_global` 恆為 0）、`IsNetlistIgnore` 語意不符（零件數對不
> 上）、一度想用「沒有 pin」當排除規則（會誤刪 47 顆真零件）。
>
> 早期用的「匯出後 byte-identical 回寫」測試**對階層錯誤完全免疫**——階層在
> 那份檔案裡是註解。**一個結構上驗不到你在意的東西的測試，提供的是假的安心。**

### 第 1 層：元件模型對得上 datasheet

追跡結果完全建立在模型上。這一層有**三種強度不同**的檢查，不可混淆：

| 檢查 | 能證明什麼 | **不能**證明什麼 |
|---|---|---|
| `verified_against` 必填 | 有人聲稱翻過那一頁 | 那一頁真的寫了這件事 |
| pin-existence（模型的腳存在於 netlist） | 沒打錯腳號、沒套錯腳數不同的衍生型號 | **封裝對不對** |
| package 解析 | 用的是哪一欄腳位表 | 那一欄的功能解讀正確 |

⚠️ **pin-existence check 不是封裝驗證。** 兩個封裝同為 1–N 而腳位定義不同時
（這是常態），它必然通過。命名要誠實——名字若叫「封裝驗證」，名字本身就在
製造假保證。

`load_models()` 會拒絕載入沒有 `verified_against` 的模型。**這個限制是刻意的，
不要為了讓追跡跑通而繞過它**——追跡停在某顆 IC，是「這裡還沒查證」的正確表現。

#### 封裝判定：證據排名，不解析 datasheet 表格

每家 datasheet 的腳位表排版都不同，通用地「看懂」是無底洞，而且一列錯位就讓
整張表作廢。改用三個來自 **netlist 與 BOM** 的證據來源（同 `mate` 的機制）：

| 來源 | 標記 | 判別力 |
|---|---|---|
| 模型宣告的電源/接地腳實際接法 | `[N 板名 refdes.pin]` | **最強**，候選封裝差最多的就是電源腳位置 |
| 訂購碼的封裝後綴 | `[B 板名 refdes]` | 強，但要模型有填 `ordering_suffix` |
| footprint 名稱 | `[N 板名 refdes.pin]` | 中，命名習慣因專案而異 |

| 判定 | 條件 | 可用？ |
|---|---|---|
| `user_confirmed` | `part_package` 明確宣告且不與 netlist 矛盾 | 可以 |
| `single_candidate` | 該料號只有一個模型 | 可以 |
| `inferred` | 零矛盾 + 唯一勝出 + ≥1 獨立佐證 | 可以，但**一律標 `[?]`** |
| `unresolved_pending_user` | 證據不足 | 不可以，列入待補 |
| `conflict` | 宣告或候選與 netlist 矛盾 | 不可以，`audit` FAIL |

⚠️ **宣告的 GND/PWR 腳在 netlist 上完全沒接 = 矛盾**，不是「資料不足」。訊號腳
可以 NC，電源腳不會。這條規則是拓樸判別力的主要來源。

**不得以已接腳數推定封裝**（見 `pitfalls.md` T2）。

### 先分辨物理型式（`Fabric.mate_form`）

看兩側連接器的**系列名**（`Conn_SEAF-20-…` → `SEAF`），不管誰公誰母：

| 型式 | 判準 | 接法 |
|---|---|---|
| 公母直接對接 | 兩側系列不同（`SEAF` 對 `SEAM`） | **一律直通**（n ↔ n） |
| 線束 | 兩側同系列（`T2M` 對 `T2M`、`UEC5` 對 `UEC5`）—— 插不起來，中間必有線 | 逐腳比 net 名 |

⚠️ 不再枚舉換排、反轉、任意排列。直接對插的接頭照原廠設計就是直通；線束
可以任意接，固定的幾種幾何候選涵蓋不到。

### 直接對接：證據只確認「這兩顆是一對」

兩個指標：

- **語意相符數** — 直通下 net 名稱正規化後相同的腳數。
- **矛盾腳數** — 兩側都被正面辨識成電源／地、但類別不同（`Fabric.contradicts`）。
  一側 `cls` 認不得（落在 `SIG`）**不算矛盾**。

定案：**語意相符 ≥ `MATE_MIN_SEMANTIC`（4）且多於矛盾**。矛盾**不否決** ——
實例 `interposer.J3 ↔ DPU.J2001` 有 12 支 `3P4V_C` 對 `3P3V_C_VDD_X`，是兩側
對同一條軌的電壓命名不同。填錯配對時則是幾乎沒有相符、到處矛盾
（`J3 ↔ J2002`：相符 0、矛盾 36）。

相符不足多半是兩側命名不同（`_P` 對 `_DPU` 後綴、`AGND` 對 `GND`）——
補 `net_normalize`，不是放寬門檻。

### 線束：每支訊號腳都要唯一對上

每支**訊號腳**（非電源／地）都要在對面找到**唯一**同名的腳，兩個方向都要；
對上了就照名稱接，不管是同號還是交叉。電源／地不必對上 —— 追訊號時本來就跳過。

| 情況 | 結果 |
|---|---|
| 訊號腳全部唯一對上 | `inferred`，照名稱對應接 |
| 兩側只有電源／地 | `inferred`，接法不影響訊號（偵測時不會自動配出來，要自己宣告） |
| 有訊號腳對不上（TX/RX 各自命名、自動命名 `N#####`） | `ambiguous`，線束接法請提供 `mate_map` |

### 配對：誰插誰

- 兩側都有多個同分候選（Primary/Redundant 設計，例如 interposer J1/J2 對
  DPU J3/J1003）—— **netlist 分不出來，一律問人**。
- 只有一側多個（一片板插到 N 個同型槽位）—— 視為扇出。

⚠️ 扇出時 N 片板在工具裡共用**一份** netlist。跨板進入那片板之後若再從同一顆
連接器走回其他槽位，N 個槽位會看起來互相接通。

### 定案狀態

| 狀態 | 條件 | 下游 |
|---|---|---|
| `approved` | `mate_map` 明確批准 | 無 caveat |
| `inferred` | 上述規則成立 | 無 caveat，標 `[?]` |
| `ambiguous` | 規則不成立 | 暫以直通佔位，掛 `mate:ambiguous`，confidence 降為 unknown |

### 兩個獨立的軸，不要混講

| 欄位 | 值 | 回答的問題 |
|---|---|---|
| `confidence` | `confirmed > caveated > unknown` | 這條結論的**證據**有多強 |
| `gating` | `always` / `conditional` / `unknown` | 這條路徑**已查證**的通斷性質 |

一條 datasheet 查證完整、package 已鎖定的 runtime-gated 路徑，證據品質是
`confirmed`、通斷性質是 `conditional`。把兩者混成一個排序，會讓它排在
「package 未佐證但恆通」之下——與事實相反，而且會誘使人為了拉高 confidence
而迴避正確標註的 conditional。

## 2. 零件分類完整說明（原 `references/part_classification.md`）

### 零件分類（這顆到底要不要查 datasheet）

`coverage` 原本把每一顆 active 平等列出，於是屏蔽罩、螺帽跟 FPGA、ADC 混在
同一張表，每一列都掛著「待查 datasheet」。那不是清單，那是雜訊——真正該先查
的東西被埋掉了。

#### 分類的權威來源是**料號**，不是 refdes 前綴

前綴是各家自己的習慣。實測某專案用 `ME` 標機構件、`OPEN` 標預留位置、
`Coupler` 標耦合器——這些寫死進工具的通用表，就是在遷就單一專案，換一塊板又
要補規則，而且補的人不會知道漏了什麼。

公司的料件資料庫（OrCAD CIS）本來就有一套**綁在料號上**的分類體系。實測 6
塊板 1509 顆 active：光靠料號查表命中 **93.6%**，查不到的只有 2 個料號。

#### 順位（第一個命中就採用）

| 順位 | 來源 | 標示 | 事實還是推論 |
|---|---|---|---|
| 1 | `ndd.json` 的 `part_class` | `(宣告)` | 人講的最大 |
| 2 | CIS 快照查表（料號） | 無標示 | **事實** |
| 3 | **footprint 樣式** | `[?]` | 推論 |
| 4 | 料號樣式（`OPEN_`／`DNP-`／`NC_`…） | `[?]` | 推論 |
| 5 | refdes 前綴通用表 | `[?]` | 推論 |
| 6 | 都沒命中 | `!!` | 未辨識，**攤出來等人確認，不猜** |

#### footprint 是主力，不是備胎

CIS 快照是內部資料，不能隨 skill 散布；footprint **就在 `.asc` 裡**，不需要
密碼、不會過期。實測同樣六塊板：

| | 有 CIS 快照 | 沒有快照 |
|---|---|---|
| CIS 查表（事實） | 1230 | 0 |
| footprint 推論 | 278 | **1462（96.9%）** |
| refdes 前綴推論 | 1 | 22 |
| **未辨識** | **0** | **25（1.7%）** |
| 分類粒度 | 17 種 | 16 種 |

那 25 顆剛好就是不該出現在公開規則表裡的東西（屏蔽罩 13、熱敏電阻 11、
天線 1），用專案本地 `part_class` 三行就收斂。

##### 這張表是怎麼來的

**從真實專案的 footprint 逐條比對 CIS 分類學出來的**——1161 顆、零衝突。
準確度來自那次對照，不是從 EDA 詞彙表挑字。字面剛好都是通用功能詞
（`ADC`、`ADC`、`BPF`、`HPF`、`Ferrite`、`OPTOISO`…），所以能出貨而不透露料號、客戶或
頻段，那是另一件事。

##### 刻意排除的（即使資料上「學得出來」）

| 學到的規則 | 為什麼不出貨 |
|---|---|
| `QFN -> rf` | **語意就錯**：QFN 是封裝不是功能，只是那批板子的 QFN 剛好都是 RF 件 |
| `R -> sensor` | **危險**：來自 `R-1Kohm`（熱敏電阻），但 `R` 是電阻通用前綴，換塊板會大規模誤判 |
| footprint 名稱嵌了料號的 | 等於換個地方公布選料清單 |
| 含客戶代號／專案代號／頻段字樣的 | 那三樣都不該離開公司網路 |

這幾條改走專案本地的 `footprint_class`／`part_class`，不進 repo。

⚠️ **footprint 推出來的一律標 `[?]`**（它是繪圖慣例，不是採購紀錄；CIS 綁的
才是實際買進來的料）。但**工具預設公司的 footprint 命名是對的**，不會去質疑
它——否則每顆都要人工複核，這個機制就失去意義。

#### 未辨識的多半是自製件——**請人工補，工具不猜**

實測剩下的未辨識全是公司自製／專案專屬的東西：屏蔽罩（專案代號開頭）、
熱敏電阻（自訂 footprint）、天線（客戶代號開頭）。這類東西沒有通用命名可循，
**猜出來的分類比空白更糟**，所以工具只列清單、不推測。

`init` 跑完會在 `SETUP.md` 的待辦列出這一項，`coverage` 表尾與 `REVIEW.md`
的 B7 也各列一次。補法：

```json
"footprint_class": { "PROJ01": "mechanical" },
"part_class":      { "ME": "mechanical" }
```

⚠️ **`source` 一定要跟著分類一起帶出去**（用 `INFERRED_SRC` 判斷）。CIS 命中
是料號查表的事實，樣式推出來的是 `[?]`。混為一談等於把推論洗成事實，而且
沒有任何症狀。

#### CIS 快照怎麼來

**唯讀 SELECT，密碼不經過 AI**，在自己的 PowerShell 跑：

```powershell
$srv='<CIS 伺服器 IP>'; $db='CIS'; $user='<帳號>'
$pw = Read-Host "密碼" -AsSecureString
$pw.MakeReadOnly()
$cred = New-Object System.Data.SqlClient.SqlCredential($user,$pw)
$cn = New-Object System.Data.SqlClient.SqlConnection("Server=$srv;Database=$db")
$cn.Credential = $cred
$cn.Open()
$cmd = $cn.CreateCommand()
$cmd.CommandText = @'
SELECT Number, Manufacturer_PN, classify_str, Part_Type_CIS, Parts_Description
FROM CIS_ALL
WHERE (Manufacturer_PN IS NOT NULL AND Manufacturer_PN <> '')
   OR (Number IS NOT NULL AND Number <> '')
'@
$dt = New-Object System.Data.DataTable
(New-Object System.Data.SqlClient.SqlDataAdapter($cmd)).Fill($dt) | Out-Null
$cn.Close()
$dt | Export-Csv '<專案>\export\cis_parts.csv' -NoTypeInformation -Encoding UTF8
```

整段只有一個 `SELECT`，沒有 `INSERT`/`UPDATE`/`DELETE`/`ALTER`/`DROP`，
`SqlDataAdapter` 只呼叫 `Fill()`（讀）沒有 `Update()`（寫）。

⚠️ **匯出的 CSV 不可進公開 repo**：那 5741 筆含 377 筆自製件（產品名、專案
代號）與 896 筆 RF 料件（頻段規格），等於公布產品線與選料清單。它的定位是
**開發 skill 時與 CIS 直接對照的依據**，留在本地（`dsn/` 已 gitignore）。

路徑用 `ndd.json` 的 `cis_snapshot` 指定（預設 `export/cis_parts.csv`）。
**檔案不在就降級成 footprint + 前綴推論**，不報錯——快照是**選用加速器，不是前提**，
與 `models.json` 的定位一致。快照的 SHA-256 要進 `MANIFEST.md`：它會改變結論。

| `1E99` | Uncategorized | 未辨識 | 等人確認 |

⚠️ **`1E99_Uncategorized` 不等於「缺分類」。** 實測 183 顆裡有 182 顆是
`OPEN_0402`——那是**刻意保留的未貼位置**，是設計事實。工具用料號樣式
（`OPEN`/`NC`/`DNP`/`DNI`/`NOSTUFF` 開頭）把它們獨立歸成 `placeholder`，
不混進「需你確認」害人去查根本不存在的規格書。剩下真的沒分好的才進清單。

#### refdes 前綴後援表

**只收真正跨公司通用的**：

`U`=IC．`Q`/`D`=分立半導體．`R`/`C`/`L`/`FB`=被動．`X`/`Y`=晶振．
`J`=連接器．`TP`=測試點．`H`/`MH`=鎖孔．`FM`=基準點．`F`=保護元件．
`S`=開關．`K`=電驛．`T`=變壓器．`W`=線材

**刻意不收**（這些是某家公司/某塊板自己的標籤，寫死就是遷就單一專案）：
`ME`、`FUSE`、`OPEN`、`Coupler`、`Cal`、`Main`、`GPIO`、`DAC`、`UC`、`AT`、
`CS`、`PO`、`CA`、`EXTOUT`、`A`、`M`。

`P` 也不收——跟「電位計」撞名。P 開頭的連接器靠 footprint 開頭是 `conn`
兜底，不會漏。

#### 未辨識的怎麼收斂

`coverage` 最後會列出「分類未辨識，需你確認」。在 `ndd.json` 補：

```json
"part_class": {
  "OPEN": "placeholder",
  "ME": "mechanical",
  "b0017_dpu_v1:A12": "mechanical"
}
```

key 可以是 `<board>:<refdes>`（單一實例）、料號、或裸前綴（整批適用）。
footprint 樣式則用另一個欄位（同樣是惰性例外表）：

```json
"footprint_class": {
  "PROJ01": "mechanical",
  "CUST-A": "pcb",
  "R-1Kohm": "sensor"
}
```

**惰性例外表，隨用隨長，不是必填清單**——跟 `part_package`、`endpoints`
同一個慣例。

分不出來的分類，`signal_relevant()` 一律當「可能重要」：漏查一顆 IC 比多列
一顆機構件貴得多。

## 3. 主說明搬出的段落（原 `SKILL.md` 判讀規則）

⚠️ **同一料號的兩顆零件 symbol 腳位名不一致時，整筆不寫入。** 那代表其中一顆
用錯 symbol，或 BOM 標錯料號——不可合併，也不可挑一個。

> **快取原文，永不快取解讀。**
> 快取的是逐字內容 + 出處（檔名／頁碼／SHA-256／封裝欄），不是「pin1 與 pin3
> 內部連通」這種推出來的結論。原文快取 5 秒就能核對；推論快取會把錯誤凍結成
> 永久資產。datasheet 換版時 SHA-256 不符會自動失效重抽。

### 封裝判定只用 netlist + BOM

**工具不解析 datasheet 的腳位表**（每家排版不同，一列錯位整張表就作廢）。改用
三個證據排名：模型宣告的電源/接地腳實際接在哪 `[N 板名 refdes.pin]`、訂購碼的
封裝後綴 `[B 板名 refdes]`、layout 的 footprint 名稱 `[N 板名 refdes.pin]`。
`audit` 的 [1.5] 段會逐顆列出判定與證據。

**推論出來的一律標 `[?]`**，並帶 `package:inferred` caveat 沿路徑傳到 CSV。
門檻是「零矛盾 + 唯一勝出 + 至少一個獨立來源佐證」，達不到就列入待補，
**不替你假設**。即使使用者明確宣告 `part_package`，與 netlist 矛盾仍會 FAIL
（**人講的最大，但矛盾要講出來**）。

### 跨板對接怎麼判讀

板子都已在實體世界接過、可以用，所以工具只判斷「怎麼接」：

- **兩側系列不同 → 公母直接對接 → 一律直通。** 直通的 net 名相符 ≥ 4 且多於
  矛盾，才確認兩顆是一對；矛盾不否決（常是兩側電壓命名不同）。
- **兩側同系列 → 線束。** 每支訊號腳都在對面唯一同名才照名稱接；對不上就問人要
  `mate_map`。只有電源／地的線束直接放行。
- **兩側都有多個候選（Primary/Redundant）→ 問人指定配對。**

| 狀態 | 條件 | 下游 |
|---|---|---|
| `approved` | `ndd.json` 的 `mate_map` 明確批准 | 無 caveat |
| `inferred` | 上述規則成立 | 無 caveat，標 `[?]` |
| `ambiguous` | 規則不成立 | `mate:ambiguous`，confidence 降為 unknown |

細節見 `references/verification.md`「跨板對接」。

### 零件分類的順位

人工宣告 > CIS 料號查表（**事實**）> footprint 樣式 > 料號樣式 > refdes 前綴
（後三者是**推論**，標 `[?]`）> 未辨識（列進「需你確認」，**工具不猜**）。主力是
footprint——它就在 `.asc` 裡，不需要 CIS 也不會過期。實測六塊板涵蓋 96.9%、
未辨識只剩 1.7%。詳見 `references/part_classification.md`。

## 4. 元件模型的設計理由（原 `references/models.md`）

手動複製是刻意的：模型是「某人對 datasheet 的解讀」，自動塞進每個專案等於讓你
在不知情下用別人的解讀去追訊號——錯了會產生看起來完全合理、但整張表是錯的
訊號鏈。複製之後它就是**你的宣告**，`audit` 與 `REVIEW.md` 才會把它列進你要
負責複核的清單。

`boundary(not_followed)` 只在 `trace --board`（板內追蹤）出現。它標在**本板
這一側**的腳位上，對面腳位只寫進 reason 字串當證據——對面的節點不進 path。
這不是潔癖：對面節點一旦進了 path，`path_caveats` 會把對接的 `mate:ambiguous`
算進**沒有跨板**的板內結論，階層加註還會拿對面的 refdes 去查本板的表，而
`U1`、`J2` 這種 refdes 每塊板都有——查到的是**別塊板的**功能名，不是查不到。
邊界那一列本身**要**背對接的 caveat（它宣稱了對面是哪支腳）。

## 5. 規格書下載的設計（原 `references/datasheets.md`）

### ⚠️ HTTP 200 不代表拿到 PDF

擋機器人的站會回一頁 HTML 而不是檔案。`_fetch()` 會驗 `%PDF-` 魔術位元且
檔案 > 20 KB，不符就刪除並回報失敗。**不要拿掉這個檢查**——存下一堆 HTML
偽裝的「datasheet」，之後查腳位時才會發現，那時已經寫了一堆錯的模型。

⚠️ `init --run` / `migrate --run` **預設不下載**（要下載加 `--datasheets`）——
升級或建專案的指令不該無預警發網路請求。不下載時照樣產生 `INDEX.md`。

## 6. 常見錯誤清單的維護（原 `references/pitfalls.md`）

### 不放進本文件的問題

以下確實存在，但不適合成為 runtime pitfall——它們是**架構／工具**問題，
多寫一條規則不會改變行為，只會增加讀取成本。

- **Skill 遵循性**（對話變長後可能忘記讀某份 reference）——context management
  問題。解法是減少 runtime 規則、改善載入機制，不是加一條「記得遵守」。
- **Routing bootstrap**（要先知道需不需要 datasheet，才能決定要不要讀
  `datasheets.md`）——routing 架構問題。解法是固定入口或工具能力。
- **驗證成本不對稱**（產生 citation 便宜、人工驗證貴）——tooling 問題。解法是
  自動產生可重跑的查詢、自動驗證高價值 inference，**不是要求我因為驗證昂貴就
  變得更保守**（那正好落進 T5）。

---

### 維護原則

新發現一個錯誤時先問：**這是新的 failure mode，還是既有模式的新案例？**

- 既有模式的新案例 → 加進該條的實測括號或測試，**不新增一條**。
- 能形成明確、可機械驗證的 invariant → 移到 code / audit / test，並把該條的
  「誰擋著」欄改掉。`MANIFEST` 雜湊比對就是 B4 的出場條件。
- 已被 `SKILL.md` 判讀原則完整涵蓋 → 不要在這裡寫第二套。
- 真的是新的判讀失敗模式 → 才新增，並描述它背後的**共同結構**，不是某一顆 IC、
  某一塊板、某一次事故。

新增輸出觸發器的門檻更高：**要寫得出文字觸發形狀**（「句子裡出現 X」），
寫不出來的就是背景認識，不要混進觸發器那段——那段的價值來自它短。

**不設條數目標。** 配額會被填滿，而填進去的必然是本該屬於某個維度的東西。

目標不是讓這份文件愈完整愈好，而是用**最少的 failure mode 覆蓋最多種「看似合理
但其實錯」的分析**。
